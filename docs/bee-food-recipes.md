# Bee food and recipe creation

Implemented locally on `feat/bee-conversation`, 2 October 2026. This extends the
existing adaptive assistant and libraries; it does not establish a production
deployment or a live Gemini result.

## What users can do

- Ask Bee to make a recipe with specified ingredients or a dish. Bee proposes
  ingredient amounts, preparation, cooking steps and a serving count. Nutrition
  is calculated from independent ingredient records, not generated by Gemini.
- Review ingredient amounts, sources, steps and nutrition per serving. Change
  ingredients or say “Actually make it 4 servings” before saving. The previous
  review cannot be confirmed after a correction.
- Confirm **Save to Cookbook**, or cancel. Saving creates a recipe, without
  recording consumption. Cookbook can edit its servings/steps and separately
  add a selected fraction or one serving to the diary.
- Create a reusable food from a matching independent record or a complete
  manually supplied label, then confirm **Save to My Foods**. Saved values use
  a clear per-100-g, per-100-ml or per-one-labeled-serving basis.
- Ask about a named saved recipe later. Its actual private ingredients and
  serving count define the answer; a public food with the same name cannot
  replace it. No cooked gram yield is assumed.

Creation belongs to **Pro adaptive Bee**. Basic manual My Foods/Cookbook and
Plus one-food assistance retain their existing access rules. A user who loses
Pro before confirming cannot complete a pending library creation.

For a manual label, quote the food name, provide exactly one basis, and separate
each value with commas. Use the actual package values, for example this format:

```text
Create food "My food" per 100 g: calories <kcal>, protein <g>, carbs <g>, fat <g>
```

Replace the placeholders; they are not nutrition data. “Per serving” also works.
An incomplete, ambiguous or malformed label asks for input, without filling in
missing values. No image-reading integration is claimed.

## Responsibilities and changed files

Gemini uses the existing stateless Interactions adapter to choose a creation
intent and draft recipe instructions. Server code resolves every ingredient,
calculates canonical nutrients and creates an exact pending review. PostgreSQL
rechecks the retained basis, portion, sources and totals and performs the library
insert only after the user's confirmation.

| Area | Files and changes |
| --- | --- |
| Creation and independent arithmetic | `_shared/beeCreation.ts`, `beeRecipeRecord.ts`, `beeNutrition.ts`, and their tests |
| Typed conversation and dispatch | `_shared/beeTypes.ts`, `beeAdaptive.ts`, `beeAdaptiveTurn.ts`, `beeConversation.ts`, `beeService.ts`, `bee-chat/index.ts` |
| Reviewed actions and database invariants | `20261002000000_bee_food_recipe_creation.sql`, `supabase/tests/creation_database.mjs`, `scripts/test-bee-db.mjs` |
| Shared client and review | `src/lib/beeChat.ts`, `BeeCreationReview.tsx`, `BeeQuickLog.tsx`, client tests |
| Existing libraries | `app/create-recipe.tsx`, `app/(tabs)/cookbook.tsx`, `app/my-foods.tsx`, `recipeDetails.ts`, `foodLibraryEvents.ts` |
| Usability and browser checks | `BeeCompanionProvider.tsx`, `scripts/check-bee-creation-ui.cjs`, updated Cookbook regression runner |

There are **no new tables or dependencies**. The additive migration extends
`recipes` with `servings`, `instructions`, `bee_action_id`, `bee_provenance`;
`personal_foods` with protected action/provenance columns; and
`bee_pending_actions` with typed library-creation payloads. Composite owner
foreign keys and unique action indices prevent cross-account references and
duplicate inserts. Existing owner-only RLS remains active.

Legacy recipes default to one serving. Their existing fraction-of-whole-recipe
diary representation is preserved. The migration also permits the existing
`recipe` diary unit, which the earlier validation constraint incorrectly rejected.
Source values are summed before final portion rounding, avoiding double rounding.
Manual edits flag Bee provenance as user-edited instead of relabeling it verified.

## Sources, limits and retention

- Ordinary public food lookup retains curated gist priority and the existing
  Google-then-USDA fallback. An exact owned Cookbook recipe is authoritative for
  its own serving. Library creation uses only independent sources: curated gist,
  owner foods/recipes, Open Food Facts and USDA. It never invokes Google Search
  to obtain reusable ingredient values or crawls grounded links.
- Original identity, serving basis, source URL/ID, retrieval time, license and
  attribution remain in private provenance. Open Food Facts attribution/license
  follows the existing source resolver; USDA records retain their identifiers.
  The operator remains responsible for rights and accuracy of curated gist data.
- Recipes are bounded to 1–8 ingredients, 1–20 integer servings and 1–8 cooking
  steps of at most 300 characters. At most two ingredient lookups run together;
  the pending review is capped at 40 KB. Missing complete macros, unresolved
  variants or unsupported conversions block the whole recipe, without dropping
  ingredients, substituting zeros or inventing density.
- One new creation turn uses the existing shared Pro request allowance. Internal
  ingredient retrieval is not another user credit. The inherited limit is two
  non-search model calls, 4,096 output tokens per call and a 55-second request
  deadline. Confirm/Cancel and a retained-source serving-count correction use
  deterministic code without another paid model call. Existing request IDs,
  reservations, failed-call accounting and replay semantics are unchanged.
- No new cache is introduced. The fixed gist is memoized only within one request.
  Google results remain transient, answer-only and excluded from library data.
  Chat retains the existing owner-scoped 30-day/bounded history policy. Pending
  library reviews expire after 30 minutes. Saved libraries retain the referenced
  review/provenance for as long as the saved item exists; clearing chat does not
  remove recipes, foods, memories or intake history.

Automated evidence checks establish structured record/basis consistency and
supported arithmetic. They do not prove that a publisher's label is correct,
that a generated recipe is suitable for every person, or that cooked yield equals
ingredient weight. Recipe instructions and ingredient completeness still need
the user's review. User-entered labels remain identified as user data.

## Setup and rollout

1. Review/back up the actual schema and apply the existing migration chain in
   timestamp order through `20260930000200_gist_food_source.sql`.
2. Apply **`20261002000000_bee_food_recipe_creation.sql`** to an isolated compatible
   database first. Its function-extension anchors fail closed if earlier RPC
   definitions differ; diagnose a mismatch instead of skipping checks.
3. Run the checks below. Deploy updated **`bee-chat`** after the migration succeeds.
4. Publish the updated web client and compatible native binaries last. Earlier
   clients cannot render library-review action kinds; use a controlled release
   window. No client should call the new columns before the migration.
5. With an operator-controlled adult Pro account, verify live recipe creation,
   retry, cancellation, cross-device reload, library editing and separate diary
   logging before broad rollout.

No additional environment variables are needed. Existing server configuration:
`GEMINI_API_KEY`, `GEMINI_MODEL=gemini-3.8-flash`, `BEE_AI_ENABLED`,
`GEMINI_PAID_DATA_USE_CONFIRMED=true`, `USDA_API_KEY`, and Supabase's server
URL/anon/service-role configuration. `GEMINI_SEARCH_ENABLED` controls ordinary
answer-only web search; creation works without that branch. A verified Pro
entitlement and the existing age/paid-data gates still apply.

See [the deployment guide](bee-gemini-deployment.md) for the full prerequisite
migration chain, provider setup, quotas and secret handling. Keep credentials in
ignored `supabase/functions/.env` or project secrets, never `EXPO_PUBLIC_*`.

Operator commands, after linking the intended isolated/project environment:

```sh
supabase db push --dry-run --linked
supabase db push --linked
supabase functions deploy bee-chat --project-ref <project-ref> --no-verify-jwt
```

The handler validates every real Auth session. `--no-verify-jwt` disables only the
gateway's legacy JWT check, not handler authentication. Review the dry run; do
not reset a linked database or apply test fixtures to production.

### Manual web/mobile release walkthrough

1. Sign in to the same test Pro account on web and one native device. Ask for a
   simple recipe using known ingredients/preparations. Review every ingredient,
   amount, source, serving count, macro and step. Verify no library/diary write yet.
2. Change servings and an ingredient. Reload the other client: only the latest
   review may save. Cancel once and verify the libraries and diary are unchanged.
3. Confirm, retry and double-tap. One Cookbook item must appear on both clients,
   with no diary change. Edit its servings/steps, select one serving, then confirm
   a separate diary addition. Verify dashboard totals refresh once.
4. Create a My Foods item from a real complete label. Check its canonical basis,
   confirm, reload and log a chosen portion separately. Missing macros or ambiguous
   basis must ask for input rather than filling numbers.
5. Try a second account's thread/action IDs, an expired review, loss of Pro and a
   provider outage. Verify denial/recoverable errors and no false saved notice.

## Security review and recovery

Security check: validated JWT-derived owners, explicit scoped queries, existing
owner RLS plus composite owner foreign keys, private RPC grants/fixed search
paths, runtime/schema validation, repeated SQL arithmetic, typed action/version
checks, atomic row locking and unique confirmation, protected provenance,
untrusted model/source text, safe source links, bounded calls and no new secrets
were reviewed and covered by deterministic/real-database checks. Model-generated
text cannot insert a diary or library row without the subsequent reviewed action.

If rollout fails, disable new AI generation with the existing `BEE_AI_ENABLED`
flag and keep manual tracking available. Leave additive columns and user data
intact, allow unconfirmed reviews to expire, and ship a forward fix. Restore a
previous client only after checking its action compatibility. Do not drop saved
libraries, referenced actions, provenance or food history as rollback cleanup.
